# PDF Workspace agent handoff

## Scope and source hygiene

- Keep application changes in `src/` as TypeScript/React code. Keep Electron process changes in `electron/` only when required by the desktop boundary.
- Do not commit generated `dist/`, `out/`, or `test-output/`; their current `.gitignore` rules must remain in place. Do not edit generated outputs to fix a build.
- Release automation is `.github/workflows/release.yml`. It runs only when a version tag matching `v*.*.*` is pushed, never on ordinary `main` pushes or pull requests.
- Never add plaintext credentials. The workflow uses only the GitHub Actions `GITHUB_TOKEN` (`github.token`) with `contents: write` permission.

## Next implementation agent

Unreleased UI/scroll source changes are described in `CHANGELOG-UNRELEASED.md`. Do not confuse the working tree/build with the published 1.0.5 installer. Read that file before the next release.

1. Start from the current committed version in `package.json` (1.0.5 at this handoff). Read its `CHANGELOG-<version>.md` and `RELEASE.md`; `DEVELOPMENT_GUIDE.md` is historical, not current status.
2. Preserve `electron/update-controller.ts`: automatic check/download, explicit restart only, no install on normal quit, fresh renderer dirty/busy safety handshake before and after confirmation, input lock during final validation, fail closed on missing replies. `scripts/update-controller-regression.cjs` mocks the updater; it does not prove an actual install.
3. Run locally: `npm ci`, `npm run typecheck`, `npm run test:regression`, `npm run build`, then `node node_modules/electron-builder/cli.js --win nsis --x64 --publish never`.
4. In a clean build output, confirm the intended version's NSIS x64 `.exe`, matching `.exe.blockmap`, and `latest.yml`; run `node scripts/verify-release-package.cjs dist`. Existing local `dist/` may contain older installers, which must not be uploaded accidentally. Never commit outputs. `public/fonts/` and `assets/fonts/NanumGothic-Edit.ttf` are generated by npm ci/build from the tracked original font.
5. For the next release, increment `package.json` AND the root/package entries in `package-lock.json`, add `CHANGELOG-<version>.md`, then commit approved source changes and push `main`. About uses the package version automatically. Create/push the exactly matching `v<version>` tag only when publishing is authorized. Do not reuse 1.0.5 for different source. A normal main push does not publish.
6. Watch the GitHub Actions run. It validates the version/tag match, tests, builds, creates a draft release, uploads all three update assets, downloads them again and compares SHA-256, then publishes the verified release. A failed upload or hash check must remain an unpublished draft, not the latest release.

## Verification boundary

CI verifies source checks, packaging, uploaded asset names, and SHA-256. It does not prove real-device behavior. Before calling a release accepted, manually verify a clean Windows installation and upgrade, monitor movement and multi-display behavior, and native Windows/Electron font rendering. Also exercise update download, explicit restart, and unsaved-work protection.
