# 설치된 TEST 2 직접 화면 검토 · 2026-11-17

## 범위

사용자가 직접 열어 둔 `Deojon PDF .NET TEST 2` 창을 실제 데스크톱에서 확인했다. 시작 상태는 문서가 열리지 않은 빈 작업 공간이었다. 검토용 3쪽 `font-render-diagnostic.pdf`를 열어 확인했고, 2쪽 회전 후 실행 취소했다. 저장은 하지 않았으며, 마지막에 시험 문서를 닫아 빈 작업 공간으로 돌렸다. 설치 앱의 모든 기능, 다른 디스플레이·DPI, 실업무 문서 전반을 확인한 것은 아니다. 본 기록의 증상은 이 설치판과 시험 조건에서 직접 관찰한 내용이다.

## 직접 확인된 문제와 개선 필요

0. **주황색 메뉴바가 중간중간 흰색으로 끊긴다.** 실제 설치판에서 상단 `기본`·`주석`·`도움말` 탭 자리가 밝은 사각형으로 드러나고 글자도 희미해, 주황색 띠에 구멍이 난 것처럼 보인다. 활성 탭의 선택 표시는 의도적인 색 구분과 별개로, 비활성 탭 영역의 배경·글자 대비가 무너진 시각적 결함이다. 사용자가 직접 지적했다. 기존 승인 디자인의 연속된 메뉴바를 유지하고, 활성·비활성·선택·마우스오버 상태를 실제 앱 화면에서 모두 확인해 수정한다. 소스에는 탭 투명 배경과 비활성 처리가 공존하므로 기본 버튼 템플릿/비활성 스타일의 영향 가능성이 있으나, 정확한 원인은 아직 수정·검증하지 않았다.

1. **축소판 중심의 조작 부족.** 3쪽 축소판에서 우클릭했을 때 페이지 관리 메뉴가 나타나지 않았다. 축소판을 위로 끌어놓자 다른 페이지가 선택됐을 뿐 페이지 순서는 바뀌지 않았다. 페이지 이동 버튼만으로는 여러 쪽 정리가 직관적이지 않다. 우클릭 메뉴와 끌어놓기·삽입 위치 표시를 우선 검토한다.
2. **페이지 보기 흐름 부족.** 2쪽에서 문서 영역을 아래로 스크롤해도 페이지 번호는 `2 / 3`에 머물렀다. 현재 확인한 흐름은 한 쪽씩 이동하는 형태다. 연속 스크롤과 전체 페이지 맞춤이 필요한지 사용자의 기존 작업 방식에 맞춰 개선한다. 현재 화면에서 바로 쓸 수 있는 맞춤 버튼은 `너비 맞춤`이었다.
3. **확대 배율 정보 부족.** 하단 `+`를 누르면 문서가 커지지만 하단 `100%` 버튼의 표시가 그대로여서 현재 배율을 알기 어렵다. `100%`는 현재 배율 표시가 아니라 실제 크기 복귀 버튼이라는 점도 구분해야 한다. 배율 표시 및 직관적인 조절을 검토한다.
4. **리본과 기능의 미완성.** `기본`·`주석`·`도움말` 탭과 텍스트 편집·자르기·주석·인쇄가 비활성 상태다. 일반적인 PDF 작업을 이 설치판만으로 끝낼 수 없다. 기능별 실제 구현 및 모듈 배포 계획에 반영하되, 비활성 상태를 구현 완료로 보지 않는다.
5. **문서 작업 영역이 아직 단순하다.** 화면에는 문서 하나와 단일 열 축소판만 보이고, 문서 탭이나 축소판 열 수 설정은 보이지 않았다. 이번 직접 시험에서는 두 파일 동시 열기나 다중 선택 동작을 따로 확인하지 않았다. 여러 문서·축소판 조작에 대한 사용자의 기대에 맞춰 검토한다.
6. **열기 흐름.** `파일 열기`는 실제 PDF를 여는 Windows 공통 파일 선택 대화상자를 띄웠다. 이는 사용자가 계획한 1.0.1의 메인폼·열기 모달을 어떤 형태로 구성할지 별도 검토가 필요하다는 뜻이지, 공통 대화상자가 모달이 아니라는 주장은 아니다.
7. **현재 단계 표시 혼재.** 상태 표시줄에 `독립 구현 · UI 단계` 문구가 남아 있다. 실제 PDF 작업을 지원하는 시험판임을 고려하면 사용자에게 전달하는 상태가 모호하다. 접근성 트리에도 화면에서 숨겨진 기존 샘플용 항목이 남아 있으나, 그것이 실제 화면에 표시된다고 단정하지 않는다.

## 동작 확인과 제한

- 실제 `파일 열기`에서 시험 PDF가 열렸고 3개 축소판이 나타났다. 3쪽 축소판 선택 시 3쪽이 표시됐다.
- 2쪽 회전 시 문서가 회전하고 제목에 `*`가 표시됐다. 실행 취소 후 `*`가 사라졌다. 저장하거나 원본 파일을 변경하지 않았다.
- `다른 이름 저장`을 누르면 저장 대화상자가 열렸으며 취소했다. 저장 후 파일 내용이나 사용자 문서 호환성은 이번 직접 검토에서 시험하지 않았다.
- 진단 PDF의 subset 글꼴 쪽에서 글자 일부가 빠져 보였다. 과거 독립 렌더에서도 같은 시험 파일의 일부가 빠진 적이 있어, 이것만으로 설치판/PdfCraft 고유 결함이나 모든 한글 PDF 문제라고 단정하지 않는다. 전체 글꼴을 포함한 3쪽의 한글 문구는 읽혔다.
- 사용자 문서의 실제 편집·인쇄·서명/양식/주석 보존, 여러 문서, 대용량·네트워크 PDF, 저장 및 설치/업데이트는 별도 검증이 필요하다.


## 대청 보고서 재현 검토

사용자가 바탕화면의 `4. 보고서(대청).pdf`를 열었을 때 앞쪽 일부 축소판만 나오고 나머지가 숫자로만 표시되며, 가운데 스크롤로 다른 쪽으로 가지 못했다고 보고했다. 원본과 SHA-256이 같은 임시 복사본(17,609,988바이트, 129쪽)으로 설치된 TEST 2에서 직접 재현했다. 설치된 Shell DLL 해시 `D646358E3262DA899D0F965F1F16100BDC76D1B9B1093D3A24A08E99D21BDCC6`은 당시 검증된 TEST 2 빌드와 같다.

- 왼쪽에서 뒤로 이동하자 87~115쪽 부근이 미리보기 그림 없이 숫자로만 표시됐다. 99쪽 숫자를 직접 선택하니 그 쪽의 본문과 99쪽 축소판은 뒤늦게 생성됐지만, 주변 페이지는 숫자로 남았다.
- 현재 체크아웃된 `PdfWorkspaceView.cs`는 처음 24쪽까지만 축소판을 미리 렌더하고, 이후에는 실제 선택한 쪽만 따로 렌더하는 구조다. 이는 관찰된 현상과 부합하지만, 앱이 모든 페이지를 백그라운드에서 차례로 처리한다고 볼 수 없다.
- 가운데 영역에서 마우스 휠을 아래로 사용하자 **현재 99쪽 안에서는 위치가 움직였으나 100쪽으로 넘어가지 않았다.** 소스에서도 본문은 이미지 하나를 스크롤 영역에 담은 단일 페이지 구조다. 사용자의 기대처럼 여러 페이지가 이어지는 연속 스크롤은 없다. 따라서 ‘스크롤이 완전히 움직이지 않는다’와 ‘스크롤해도 다음 쪽으로 넘어가지 않는다’를 구분한다.
- 개선 요구: 문서 전체를 사용자에게 실제 축소판으로 제공하고, 가까운 쪽부터 비동기로 채우며 진행·캐시·취소와 큰 문서 성능을 고려한다. 가운데는 연속 페이지 스크롤, 부드러운 이동과 현재 쪽·축소판 동기화를 제공해야 한다. 성능을 이유로 뒷쪽을 영구적으로 숫자만 두지 않는다. 이 내용은 개선 계획이며 아직 구현·검증하지 않았다.
- 검토는 읽기/보기만 수행했고 저장하지 않았다. 원본 SHA-256 `521E5659E143C9BC45D04C6B2CDF9D5CAE2FBBD711663CE75EE81B556527AB01`은 검토 전후 일치했다. 이후 임시 복사본은 닫고 앱을 빈 작업 공간으로 되돌렸다.


## 기존에 확인한 축소판 UI가 사라진 원인

사용자는 초기 3쪽 시험에서 축소판 카드 선택·이동·크기 조정이 잘 됐는데 실제 PDF 설치판에 왜 적용되지 않았는지 지적했다. 소스 대조 결과 기존 `Presentation/PreviewWorkspace.cs`에는 축소판 크기 슬라이더, 다중 열 배치, 선택·드래그·삽입 위치 표시 등의 화면 동작이 남아 있다. 당시 사용자가 확인한 조작은 실제였으나 데이터 모델은 합성 샘플의 메모리 상태였고, 실제 PDF 파일 조작까지 이미 연동됐다는 증거는 아니다.

실제 PDF를 연결할 때 `MainWindow.Pdf.cs`는 기존 샘플 작업 본문을 감추고 새 `PdfWorkspaceView`를 배치하도록 구현했다. 새 화면은 별도 `ListBox` 기반으로 작성되어 기존 축소판 카드·크기 조절·드래그 및 삽입선 구현을 사용하지 않는다. PDF 데이터만 연결하고 승인된 기존 사용자 조작을 유지했어야 하는데 별도 단순 화면으로 대체한 것은 구현상의 판단 오류이며, PDF 처리기나 사용자 파일 때문에 불가피했다는 근거는 없다.

다음 단계는 기존 승인 UI/상호작용을 기준으로 실제 문서 세션에 연결하는 것이다. 샘플 데이터 구조를 그대로 실제 PDF라고 취급하지 말고 화면 조작과 실제 페이지 작업·저장 계약을 분리한다. 카드 단위 선택·다중 선택, 축소판 크기/다열, 드래그·카드 좌우 삽입선, 우클릭 페이지 메뉴, 본문 연속 스크롤 및 전 페이지 축소판을 복원·연결한다. 대청 129쪽 복사본 등 실제 PDF에서 성능·결과와 원본 보호를 검증하고 사용자가 실행 화면을 직접 확인한다. 현재는 원인 분석·계획일 뿐 수정 완료가 아니다.


## 영역별 DLL 및 핀셋 패치 구조 점검

사용자가 각 화면 영역을 DLL로 분리해 메인폼이 불러오고 영역별로 패치하는 구조가 제대로 구현됐는지 의문을 제기했다. 설치된 TEST 2의 최상위에는 `Workspace.Shell.dll`, `Workspace.Runtime.dll`, `Workspace.Contracts.dll`, `Workspace.Desktop.Contracts.dll`이 있고, `Modules` 폴더와 `modules.json`에서 실제 등록된 별도 기능 모듈은 연결 확인용 `Workspace.FoundationModule.dll` 하나다. 이는 여러 DLL이 있더라도 축소판·본문·리본 등 각 영역이 독립 DLL이라는 뜻은 아니다.

현재 소스에서 기존 샘플 작업화면과 새 실제 PDF 작업화면, 축소판·본문·리본 연결은 모두 `Workspace.Shell` 프로젝트에 있으며 `MainWindow.Pdf.cs`에서 `PdfWorkspaceView`를 직접 생성한다. 따라서 사용자가 의도한 **각 영역별 DLL 교체/핀셋 패치 구조는 현재 시험판에서 구현되지 않았다.** 모듈 명세와 진단 모듈 로딩은 초기 기반일 뿐이다. `ModuleLoader.cs`는 기본 `AssemblyLoadContext`로 불러오므로 영역별 로드·해제·실행 중 교체를 현재 지원한다고 주장할 수 없다.

이 구조적 문제는 앞서 실제 PDF 작업화면을 별도로 만들어 기존 승인 축소판 UI를 감춘 문제와 함께 검토해야 한다. 특정 영역 하나만 DLL로 빼면 자동으로 안전한 무중단 패치가 되는 것도 아니다. 1.0.1 계획에 맞춰 메인폼/열기 모달을 기본 뼈대로 두고, 승인된 기존 UI를 보존하면서 실제 영역별 모듈 경계·공통 문서 상태·기능 계약·의존성·모듈 설치 및 해제/재로딩·오류 복구·테스트를 정해야 한다. 구체적인 DLL 개수와 경계는 추가 설계·검증할 사안이며 현재 구현 완료 사항이 아니다.


## 초기 열기 모달이 보이지 않는 문제

사용자는 초기 시험 때 메인폼에 열기 모달이 있었는데 현재 설치판에서 보이지 않는 점을 지적했다. 소스에서 기존 `MainWindow.Files.cs`는 메인창을 소유자로 하는 `SampleFileWindow`를 `ShowDialog`로 띄웠다. 다만 그 모달은 당시 가상 샘플 목록을 선택하는 UI였으며, 실제 PDF 파일을 읽는 기능까지 검증된 것은 아니었다. 현재 실제 PDF 작업대의 `OpenDialogAsync`는 이 화면을 사용하지 않고 Windows `OpenFileDialog`를 바로 호출한다. 실제 설치판에서도 공통 파일 선택창이 열리는 것을 확인했다. 따라서 Windows 창이 모달이 아니라고 단정할 문제가 아니라, 사용자가 직접 확인한 **앱 전용 열기 모달과 그 작업 흐름이 실제 PDF 경로에 반영되지 않은 문제**다.

1.0.1 기본 뼈대에는 사용자가 확인했던 메인폼 소유의 열기 모달을 기준으로 실제 파일 선택과 연결하는 흐름을 검토한다. 기존의 가상 샘플 목록 자체를 실제 파일 탐색기로 오인하지 않고, 모달의 시각·동작은 원본을 직접 비교하고 사용자와 확인한다. 이는 요구/개선 방향이며 복구 완료를 뜻하지 않는다.
